# 10. Completions and the man page are derived from the contract

Status: accepted.

## Context
A package that ships without shell completions and a manual page is half finished, and hand-written
ones drift: a flag is added to the code and nobody remembers the completion file. snapall already
declares every flag, variable, command scope, legal value and summary once (ADR 5), so both are
that same knowledge in other clothes.

## Decision
- **Generated by the program, from its own contract.** `snapall completions SHELL` and
  `snapall man` call argenv's `generate` module (argenv-resolve 0.3) over `Contract::records()`.
  Nothing is written by hand and nothing is a template in this repository.
- **Shipped by every artifact.** The .deb, .rpm, Arch package, Nix package and tarball install bash,
  zsh, fish and nushell completions and `snapall.1.gz` (`packaging/build-packages.sh`, the PKGBUILD
  and the flake). Paths follow each shell's vendor convention (`bash-completion/completions`,
  `zsh/site-functions`, `fish/vendor_completions.d`, `nushell/vendor/autoload`, `man/man1`).
- **Reproducible.** The man page date is `SOURCE_DATE_EPOCH` (declared in the contract for `man`, so it
  is validated and documented like any input), tar entries are sorted and owned by root, and gzip
  records no name or time. Two builds of the tarball, .deb and .rpm are byte-identical.
- **Generated on the architecture they are built for.** The build runs the binary it just built, so
  releases build natively on each architecture (they already did).
- **Tested in real shells against this contract** (`packaging/test/completions.sh`): bash word by
  word, fish with `complete -C`, zsh in a pseudo-terminal pressing Tab, nushell by loading the externs,
  the man page through groff. The same flag scoping that `lint` enforces is what the completions offer.
- **The package tests also compare** the installed completion with what `snapall completions`
  prints, byte for byte.

## Considered
- Shipping hand-written completion files: drift, which is exactly the problem.
- A `build.rs` that generates them: the generators live in argenv's runtime crate and need the
  finished contract; a subcommand is simpler, testable and useful to users without a package.
- Completing config names and snapshot ids dynamically (asking snapper at completion time): useful,
  and separate work; the completions here are static and need no running snapper.

## Consequences
A new flag, variable or command appears in the completions and the man page with no further change,
and the shell tests fail if the scoping rule and the completions ever disagree. Upgrading argenv can
change the generated text; the byte-for-byte comparison in the package tests only compares within
one build, so a review of the diff is the check for that.
